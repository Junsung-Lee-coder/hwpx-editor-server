# Native lifecycle: source contract and acceptance boundary

## Locked dependency and public API

- pyhwpx **1.7.2** wheel SHA256 `c79d6aa67baae9cd82fd7ae11217e985fa2fe832c61a09a2715aae854a0d1349`; `pyhwpx/core.py` SHA256 `a598f4a5a288fc69a9d289248ec0e6efec3c3c1ef47689381d0f4ff89124b256`.
- The original `Hwp(new=True, visible=True, register_module=False)` constructor itself calls `pythoncom.CoInitialize()`. The owning runtime also initializes COM. Its `on_quit=False` destructor unconditionally calls `CoUninitialize()` and does not Quit. Both balances must complete on the original STA.
- `save(save_if_dirty=True)` directly returns `self.hwp.Save(save_if_dirty=save_if_dirty)`. `IsModified` directly forwards to the SDK. True saves only when modified; False **as an argument** forces saving. This product never changes that argument. The clean-noop decision instead uses an exact typed False observation to avoid invoking Save at all.
- `clear(option=1)` forwards to `Active_XHwpDocument.Clear(option=option)`. `quit(save=False)` always calls `clear()` for an ordinary named document, then `self.hwp.Quit()` **without returning its value**. Neither a wrapper return nor a Boolean invented by a fake can prove native exit.
- Hancom's [public Automation guide](https://developer.hancom.com/hwpautomation) links [HwpAutomation_2504.pdf](https://github.com/hancom-io/devcenter-archive/raw/main/hwp-automation/HwpAutomation_2504.pdf), SHA256 `917142de2704ae037b0132f5a344ce5331b1fd96cc19dd574666aaacfbf0268c`. Printed pages 29 and 51 declare Clear **void**; option 1 discards. Printed page 48 describes DocumentID and Save/Close semantics. Clear is not process closure.
- Hancom's [Quit/Release guidance](https://forum.developer.hancom.com/t/topic/1168) says to call HwpObject.Quit then release; [single-document Close guidance](https://forum.developer.hancom.com/t/close/3042) distinguishes closing a document (which leaves a blank window) from Quit (which exits Hwp.exe). Quit is treated as a void call, never Boolean success. A returned None proves only return-arrival; separate exact-handle exit and COM completion are mandatory.

## Existing runtime integration

Before construction, read the existing Hwp.exe PIDs. After the actual factory returns, bind the original wrapper and dispatch, constructor HWND, DocumentID and an exact native process handle. Reject a pre-existing PID, wrong image/session, unknown generation or mismatched window. This is a private normal-close ownership guard, not an operator termination API.

On normal close, revalidate the same wrapper/dispatch, process generation/window, exact one-document/one-window counts, DocumentID, working-copy paths and exact clean flag. The clean flag is necessary, not sufficient: the service passes retained binding dirty state into the manager/STA before commands and close (including stale-binding cleanup). The STA separately retains possible-edit preservation debt through clean-noop, export and later clean projections. Close rechecks it at dequeue and again at the original native finalizer boundary, before Quit. A deliberate refusal retains the live STA, registry and managed files; it does not prevent a later healthy explicit Save.

Only an ordinary Save with an exact `True` return, all existing file/custody/location readbacks, a successful semantic outcome and journal completion can discharge normal-close preservation debt. An uncalled Save, `False`, unknown return, failed readback, timed-out command or failed reporting cannot do so. The original sticky lifetime-invocation history is never reset. The existing separately preserved and durably acknowledged recovery path retains only its original context-specific cleanup authority; no new recovery/discard bypass is added.

After those guards, raw `hwp.hwp.Quit()` is invoked once; no wrapper quit, Clear, automatic Save, forced save or teardown retry is used. Verify the original handle signalled exit before releasing any COM balance. Unknowns/errors preserve the original STA and registration, including a constructor/open failure; no later SDK teardown occurs.

After proven native exit, retire only the original pure-Python wrapper's destructor using a same-layout subclass with a no-op destructor, **before** explicitly calling the original locked destructor once. Release its dispatch references before that call. This prevents Python's later GC from running the constructor COM balance twice or on another thread. Class retirement performs no COM operation and replaces neither the original constructor object nor its SDK interface before Quit. The exact vendor constructor/destructor/property bodies are retained in `tests/fixtures/pyhwpx_172_lifecycle.py`, mechanically authenticated against the locked wheel, and executed through the real factory/STA/finalizer with fake SDK/OS boundaries. A destructor/COM failure is held, not retried.

Only after native exit and both COM return boundaries are complete is close marked succeeded/completed. Later journal/status/managed-file errors retain the completed native status and files for reporting-only cleanup, never rerun Quit. Ordinary UNKNOWN custody/reconciliation and role/protection gates are unchanged.

## Evidence limits

This source candidate is not Windows native acceptance. In particular, raw Quit returning, original-process exit while references remain, native pywin32 reference release, constructor/open DocumentID continuity, and the installed SDK/type-library void contract must still be observed in the separately reviewed/fresh BOOK gate. A timeout/failure at any boundary is held; no operator force termination can substitute for normal product completion. Portable fakes and the exact vendor Python bodies do not establish those native facts. Historical failures and consumed packets remain unchanged.
